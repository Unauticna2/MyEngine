MyEngine R12 — контракт сервера транзакций

Для обычных донатов достаточно donationUrl в payments.json и Open donation.
Эта интеграция нужна, когда игра должна узнать о подтверждённой оплате.
Сервер и подключение к платёжному сервису разворачивает разработчик.
Адрес checkoutApi задаётся в редакторе. Далее пути относительны к нему.
В запросах/ответах JSON, HTTPS, без перенаправления API на другой адрес.

1. POST /checkout
Content-Type: application/json
{"product":"coffee","requestId":"<случайный ID из игры>"}

Сервер выбирает сумму/валюту/товар по своему каталогу, создаёт платёж у
провайдера и сохраняет соответствие requestId → платёж. Повторный requestId
должен возвращать тот же платёж, а не создавать ещё один.
Не доверяй цене или праву получить товар, переданным клиентом.
Ответ:
{
  "product": "coffee",
  "id": "order_123",
  "pollToken": "<случайный непрогнозируемый токен чтения этого заказа>",
  "checkoutUrl": "https://.../страница-оплаты"
}

id: 1..128 символов A-Z a-z 0-9 _ -.
pollToken: 16..2048 символов A-Z a-z 0-9 . _ ~ -.
Для токена используй криптографическую случайность; это не API-ключ магазина.
Клиент откроет checkoutUrl только после такого ответа.
Ответ не доказывает, что платёж уже прошёл: состояние игры остаётся pending.

2. GET /transactions/order_123
Authorization: Bearer <pollToken>

Сервер проверяет токен и возвращает:
{"product":"coffee","id":"order_123","status":"pending"}
Допустимые status: pending, succeeded, canceled, failed.
Сервер выдаёт succeeded только после проверки оплаты у провайдера,
например через проверенное уведомление и/или запрос его API.
Проверяются сумма, валюта, магазин, ID и окончательный статус оплаты.
Возврат браузера на success URL сам по себе ничего не подтверждает.

Состояния клиента:
idle      — этот key ещё не запускался;
creating  — отправлен POST;
pending   — ссылка получена, идёт ожидание статуса;
succeeded — сервер подтвердил оплату;
canceled  — отменено на сервере;
failed    — сервер сообщил окончательный отказ;
unknown   — POST мог пройти, но ответ потерян, либо истекло ожидание.

POST автоматически не повторяется. Его неопределённый исход не превращается
в failed. Запросы статуса идут раз в 2 секунды, после сетевой ошибки раз в 5.
Через 30 минут клиент переходит в unknown. Таймаут одного запроса 10 секунд.
Все запросы идут в фоновом потоке; никаких сетевых ожиданий в кадре.
Сессию можно продолжить при смене сцены в рамках той же игры. После закрытия
игры состояние клиента теряется; постоянный учёт покупок ведёт сервер.

BLUEPRINTS
Кнопка: UI Click → Transaction start {product:"coffee", key:"coffee_order"}.
Выход next означает «запрос поставлен в очередь», не «оплачено».
В другом графе: Update → Branch; условие — Transaction paid once
{key:"coffee_order"}; true → показать благодарность / сменить локальный UI.
Transaction paid once возвращает true единожды для этой транзакции.
Обычный Transaction is {state:"succeeded"} остаётся true и подходит для
длительного отображения состояния, а не повторной выдачи награды каждый кадр.
Transaction reset разрешает следующую покупку после succeeded/canceled/failed.
Сброс creating/pending/unknown запрещён: сначала выясни исход на сервере.

PYTHON
payments = world.transactions
payments.donate()
payments.start("coffee", "coffee_order")
status = payments.state("coffee_order")
message = payments.error("coffee_order")
if payments.paid_once("coffee_order"):
    world.log("Спасибо за поддержку!")

Выдача оплаченных товаров, защита от повторной выдачи, привязка к аккаунту
игрока и возвраты должны учитываться сервером. Клиентский bool можно изменить
в модифицированной игре, поэтому он годится для интерфейса, а не как
доказательство оплаты для доверенного серверного инвентаря.
Никаких платежей при разработке/тестах этого обновления не совершалось.
